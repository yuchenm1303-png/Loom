# 发送：消息沿 Material 弧线飞进对话（2026-10-18）

起因：上一版（`docs/send-lift-2026-10-17.md`，已推送）之后用户说：“现在是基本接近匀速飞出，曲线也是一个很明显的向上弯的弧线，感觉动画很初级，也不一定要非常华丽的动画，我就想做成简约高级的……”，随后又说“可能也不需要缩放那些，我也不知道怎么才能做好成熟的发送动画，要不你先看看开源项目和网上的设计思考一下”。
我先去读了成熟实现的源码和设计规范，做了一个可以现场点着比的对比页（A–E 五种），用户选了 **C：Material 的四分之一椭圆弧**（“我觉得这个好看，我们就做这个吧，你随便发挥”）。这一版就是把 C 做成正式版，并把比较时留下的几处毛病一并修掉。
机制没动：落点预测与跟踪、保留真实条目、首页淡出、引导、减少动态、版式交接（躲在面纱后面）、占位符规则。换掉的是**路径、时钟、和“放下”的依据**。
实现：`src/sendFlightMotion.ts`（运动，纯函数）+ `src/sendFlight.ts`（DOM）+ `src/components/send-flight.css`。

## 一、研究：成熟的发送动画是怎么做的

- **Telegram（开源，我直接读了数值）**。iOS `ChatMessageTransitionNode.swift`：0.3 s；横向曲线 `(0.23, 1, 0.32, 1)`，纵向 `(0.1992, 0.0106, 0.2792, 0.9103)`（慢起步的 S 曲线），容器按两条曲线分别从输入框的位置移到气泡；`animateContentFromTextInputField`：气泡背景的 frame 从输入框的背景 frame 变到气泡，输入框的字 0.1 s 淡出、气泡自己的字 0.08 s 淡入，字沿纵向曲线移动（所以字和底板并不刚性地一起动）。Android `TextMessageEnterTransition.java` + `ChatListItemAnimator`：250 ms，纵向同一条 S 曲线，横向是 ease-out 套 ease-out-quint，字从输入框字号缩放到气泡字号。**没有阴影、没有抬起、没有压扁拉伸、没有回弹、没有倾斜。**
- **Material M1 运动规范**：向上的斜线运动“先浅后陡”（水平先走、垂直后到：路径向下方、也就是“绕过拐角”弯）；沿单一轴的运动不走弧线；时长手机约 300 ms，大的 375 ms，超过 400 ms 容易显得慢；桌面更短；远的路程用更长的时间。
- **Apple WWDC18 803（Designing Fluid Interfaces）**：弹簧不必弹，调的时候从 100% 阻尼（没有过冲）开始；只有驱动运动的手势本身带动量才给一点回弹。回车是按键，没有动量，所以不该有回弹。
- **别人的实现**（Cursor-for-Android、rome-os 的 PR）：也是“一个副本在覆盖层里飞、落到真实气泡上交接”，没有额外效果。

## 二、上一版为什么显得“初级”（用 `flight-curve.mjs` 量到的）

- **接近匀速**：横竖各一条刚度不同的弹簧叠在一起，速度被拉成一段平台：最高速的 80% 以上占了约 21–25% 的时间（单条曲线是 11–15%）。
- **弧线的方向反了，而且不像弧**：先垂直冲、再水平滑，路径向上拱；Material 和 Telegram 都是水平先走。
- **0.46–0.56 s 对一个每天做很多次的桌面动作太长**；
- 我把别的次级动作都去掉以后，只剩下这条曲线本身，曲线就必须好。

## 三、这一版

### 路径：一个四分之一椭圆

- 向上的飞行（总是这样，除非窗口异常）：**水平先走，到了输入框那一排的水平线以后再向上抬进位置，到位时是竖直向上的**。数学上是 `(dx·(1 − sinθ), dy·cosθ)`，θ 从 0 到 π/2；在“剩下的份额”坐标里就是一个四分之一圆。对角线飞行（`-367,372`）的最大弯度是路程的 21%。
- **沿单一轴的飞行是直线**（Material 规范：不为单轴运动画弧线）。四分之一椭圆在一边很短时会退化成一条起步很慢的直线，所以按“短边 / 长边”在 0.02–0.12 之间平滑地混进直线：两边都有一定长度（≥ 0.12）才是完整的弧。折行消息的气泡左缘通常和输入框的字几乎对齐，这是它们的路径。

### 时钟：一条标准曲线

- Material 的标准曲线 `cubic-bezier(.4, 0, .2, 1)`：从静止出发，约三分之一处最快（峰值在 28–38%），之后大部分时间在减速进位，到位时速度为零。
- **时间随路程增长，但被夹住**：`310 + 0.11 × 距离` ms，限制在 330–420。用户选 C 时看的那一条（`-367,372`，523 px）是 367 ms（比较页上是固定的 340 ms）；很短的跳 330；很远的 723 px 是 390。最高速度：1.3k（短）–6.3k px/s（远的水平扫过，约每帧 105 px）。作比较：Telegram 的横向曲线起步斜率是 4.35 × 路程 / 时间，700 px 用 0.3 s 的话第一帧就是约 10 000 px/s。

### 胶囊：还是“被拎起、带过去、放下”，只是放下的依据换了

- 药丸 + 阴影 + 气泡底色（`skin`、`halo`、`card`）；阴影就是“离页面的高度”，药丸在高度为 0 时让位给气泡自己的底色。没有缩放、拉伸、倾斜、回弹、文字的滞后（这些在比较页上试过或上一版里有，用户说不需要缩放那些）。
- **高度和材质的交接由时钟驱动，不再由“沿直线走了多远”驱动**：对平的弧（长对话里的短消息，`-650,110`），沿直线的“已走份额”在水平扫过时就到 98% 了，药丸那时就消失，而胶囊还要再抬升 100 px。现在按时钟的进度（0 = 输入框，1 = 静止）：高度在时钟 0.5 → 0.96 之间落下，药丸在 0.8 → 0.985 之间让位，气泡底色在 0.74 → 0.97 之间进来。结果所有飞行的交接都发生在差不多同一个时间份额：落下在 69–71%，药丸消失在 78–80%，底色满在 73–75%（以前平的弧是：药丸消失时还剩 28 px、还在 670 px/s）。用户看的对角线那一条几乎没变（药丸消失 76% → 78%）。

### 顺手修掉的

- **着陆的修正**：页面自己的跟随滚动在飞行结束后还会缓动约 100 ms（真实条目在交接时还在以 ~75 px/s 动），而跟踪用的滤波是 55 ms：交接时落后约 4 px，就会触发一次 110 ms 的“修正滑动”。老版本（已推送的）在 4 次里有 1 次，换成更短的飞行后 4 次里有 2 次。现在滤波的时间常数随“进到哪”从 55 ms 收紧到 10 ms（`55 − 45 × blend`，和决定“瞄现在的位置还是将来的位置”的 `blend` 是同一个量）：窗口高 480 / 560 / 640 / 720 各 5–10 次，**25 次全部不需要修正**。
- **“思考中”的一行在胶囊到达时放出**（时钟到 97%），不再是“到达时间的 86%”：它是消息之后才有的东西，而且自己有动画。这条改动也解释了一个一开始量到的差：到达的定义换成时钟以后，旧公式让它早放出约 90 ms，首次发送的 GPU 主线程忙碌时间因此多了约 100 ms（把飞行拉长 25% 差距不变，说明不是速度的事）；改成到达时放出后两者持平。

## 六、没做、可以做

- **Telegram 式的“容器变形”**：气泡的背景从输入框的整行（822 px 宽）收窄成气泡，而不是在字周围“长出”一颗药丸。药丸圆角在 2.7 倍横向缩放下会变成椭圆，需要九宫格或 clip-path（后者不在合成器上），没做。现在是：药丸出现在字周围，折行消息有“躲在面纱后面的版式交接”。
- 输入框一侧的反应（退一下、顶边亮一下）：仍然没做，每次发送多一个效果。
- 折行文字逐词/逐行的重排（FLIP）：N 个合成层，对富文本不好办。
- 发送失败时飞回输入框。
- 有头 Chrome 抓真实合成帧：这台机器上窗口被节流，验证仍是冻结跳帧（它说的是动画“说了什么”，不是显示器“画了什么”）；用户的真实 Electron 窗口里我没有看过。

## 七、坑

- `WebFetch` 在这里不能用（它依赖的小模型不存在）：用 `curl` / `gh api` 加一个去标签的小脚本读网页和 GitHub 源码；`gh search code` 能找文件路径，再用 `raw.githubusercontent.com` 取。
- 内置浏览器窗格必须是**显示着的**（`preview_start` 带 `url` 可以重新打开）才会跑动画，否则 `land` 的保险计时器先到；窗格常常只有 280–420 px 宽，对比页（镜像里的 `send-lab.html`）会提示拖宽。
- 镜像里的文件是 CRLF：用 `node -e`/heredoc 写含反斜杠、反引号的补丁几乎一定被 shell 搞坏（这次又碰了两次），用编辑工具写成文件再 `node file.mjs`，并在补丁里先把 `\r\n` 换成 `\n`、写回时再换回去。
- 在共享工作区里做反复调参、拍帧、改坏的视觉工作，放镜像里（`git archive HEAD desktop-react` + `node_modules` 目录联接 + 自己的 `cacheDir` + 自己的端口），定稿后一次性拷回。镜像开了一段时间以后，HEAD 可能已经被别的会话推进了：要先把镜像刷新到当前 HEAD 再叠上自己的文件（这次就碰到 `Composer.tsx` 等引用了镜像里没有的新模块，`tsc` 报错）。
- 判断“有没有变重”要在同一个基上对比：另起一份纯 HEAD 的镜像跑在别的端口，交替跑；并且要找原因再下结论：这次一开始看到的“+100 ms”不是飞行本身，是思考行放出时间提前了。

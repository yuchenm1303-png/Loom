# 执行节奏调查与实施方案

日期：2026-10-08。代码基线：162c6e32。本次只调查，不修改运行逻辑，不发真实模型请求。

## 结论

当前问题是模型频繁生成用户可见旁白，加上界面按助手文字切断工具分组。运行时没有要求每次调用都播报，也没有必要再增加关键词判断、额外审查模型或调用次数门槛。减少文字生成与改善呈现是两个独立目标，不能用折叠界面冒充模型执行效率提升。

## 已核实的生产路径

- `app/agent_runtime/system_prompts.py`：当前 v10 已要求初始简短说明、阶段成果/发现/阻塞时反馈，并明确不带工具调用会结束回合。8–12 次调用播报规则只存在于旧默认模板的迁移集合，不是当前默认指令。
- `app/agent_runtime/context_composer.py`：稳定前缀含主提示与 CONTEXT_PROTOCOL；后者重复了部分沟通要求。动态上下文按历史锚点重放，普通助手旁白也保留在历史中。已有冗长执行模式可能继续影响后续生成，但该因果关系尚未通过对照实验确认。
- `app/agent_runtime/runtime.py`：请求经统一 composer 组装。并发只执行工具明确允许、权限允许且绑定有效的连续前缀；有依赖的浏览器操作需要串行。不是所有单工具回复都意味着调度器失效。
- `app/agent_runtime/turn_runner.py`：带工具的助手文字标为 commentary，最终文字标为 final_answer；没有运行时伪造旁白。当前贴纸系统提示构建函数未接入请求，不能把旧贴纸注入当作现行根因。
- `desktop-react/src/components/Transcript.tsx` 的 groupTranscript：任何非 activity 项都会结束当前工具分组。因此即使每条旁白很短，仍形成“说一句、做一下”的视觉节奏。
- `app/app_server.py`：已有 canonical text、display text 与 phase 的区分，可保留完整记录，不需要根据正文关键词重新分类。

## 确定的实施方案

1. **先固定生产请求契约。** 用真实请求组装入口覆盖默认、项目指令、压缩恢复、换模型等路径，记录实际指令来源和长度。沟通策略只保留一个拥有者，合并主提示与 CONTEXT_PROTOCOL 的重复内容，而不是再追加一段更强烈的要求。项目指令与用户偏好仍按明确优先级处理。
2. **区分输出职责。** 模型文字用于发现、成果、方向变化和需要用户处理的事项；工具记录负责普通执行过程；等待状态由现有运行状态显示。无需每步确认，也不强迫模型每隔固定次数发言。保留原始模型文字供审计，不用关键词删除或改写历史。
3. **保持依赖正确的工具执行。** 检查工具描述与模型请求是否准确暴露现有批量能力；独立读取可以合批，依赖上一步结果的浏览器动作保持串行。先定位模型没有选择批量还是提供方没有收到能力，再决定修改哪一层，不增加自动猜测依赖的调度器。
4. **调整工具过程呈现。** commentary 可以成为执行过程区内的有序说明，不应天然把每个工具拆成独立卡片；最终答复和用户消息仍是明确边界。完整展开时按原顺序呈现所有文字与调用，折叠时显示过程摘要与最近说明。阶段说明是否在正文保留，应依据显式消息类型/用户展示偏好，不靠“收到”“继续”等词过滤。先用真实记录制作交互夹具验证信息可见性，再实施布局。
5. **用真实对照验证模型行为。** 在用户授权真实请求后，以同类任务对比新会话与长历史恢复、至少两个模型。记录旁白占比/字符量、有效工具工作量、耗时、输入及输出 token、计划与证据完整性。指标用于评估，不作为运行时终止阈值。若请求契约正确而频率仍高，应明确报告模型遵循差异，不能宣称单靠架构保证所有模型节奏一致。

### 处置

- **过程旁白改为小字笔记。** 工作记录里的 commentary 沿用原消息渲染器、全文和文档顺序，但显示为 13px 的灰色说明，与工具行标签对齐，不再带消息工具栏；最新一条保持较高对比度；超过约 420 字或 6 个换行的折叠为 5 行，一键展开，不丢字。开头的一句说明、最终答复、决策、审批、错误的呈现不变。这是显示密度规则，不判断内容是否重要。
- **实时区最新一条旁白从第一帧起就是笔记。** 第一版上线后用户反馈“复述先以正常大小出现，再突然缩小进入工具链”。原因是实时视图只渲染`liveTaskProgress`切出的“当前一步”，切片从最新一条旁白开始，它前面没有工具，分组函数把它当成独立消息；下一步到来时它被收进“较早过程”，排在工具后面才变成组内小字。现在 `Sequence` 把这类独立旁白也按笔记渲染，前提是它不是“回应用户的那一句”。
- **回应用户的那一句保持普通消息，在任何视图里都不变大小。** 判定只看位置，不看文字：每条用户消息（包括中途补充要求）之后、任何工具工作之前的第一条 commentary（`initialUpdateIds`）。它被收进“较早过程”后因排在工具后面落入工具组时，也按普通消息渲染（`task-flow-reply`），避免换了位置就换大小。
- **请求日志记录实际生效的进度档位**：`model_requested.progress_feedback`，取自冻结进请求的系统提示，而不是会话里保存的默认值。
- 把昨天遗留的红灯收尾：Host 服务调用 `set_progress_feedback` 后，测试里的运行时桩没有同步，另有一条系统提示断言没有跟上沟通策略。
- 未做：汇报通道、按模型分档的默认折叠。前者没有证据表明模型会用，后者需要先用 `narration_cadence.py` 积累数据。

## 2026-10-09 第二轮：工具链太长、旁白太碎

用户用新版跑了一次真实验收（同一会话第 3 回合，26 分钟、73 次模型回复、76 次工具调用），反馈：工具调用一长串、堆多了卡、小字旁白不想看，只想在阶段结束时看到重点。

### 先分清是模型还是 agent

76 次调用里 **16 次是 `tool_search`**（21%），另外 16 次 `exec`。核心浏览器工具（`browser_open`、点击、输入、按键、截图共 17 个）从第一次请求起就在工具列表里，但模型一直在搜它们，并写下“核心浏览器工具尚未出现在可用列表”。

原因在 `tool_search`：它只在“延后加载”的工具里搜。模型去搜自己已有的工具，得到的是空结果（`press key keyboard`、`screenshot`）或一堆不相干的延后工具，于是以为工具不存在，换词再搜。这是 agent 的缺陷，不是模型笨：另一个会话（439c7426）里模型也曾断言“当前会话没有任何浏览器自动化工具”，直到某次直接调用才发现“真的能用”。

修复（`tool_search_runtime.py`）：搜索范围改为模型能调用的全部工具；命中已在当前步冻结工具表里的（或本回合已激活的），结果明确写“Already in your tool list, call them directly without searching again”，并在 `data.already_available` 里列出；真正未命中时说明“工具列表里的工具直接按名字调用，搜索只找还不在其中的”。判断“已可用”以当前步的工具表为准，而不是猜。工具描述同步改了。

### 界面

- **旁白默认不画。** 非“回应用户”的 commentary 不再进入工作记录，不挂载 Markdown，也不参与“正在说话”的判断（否则流式的隐藏旁白会让思考胶囊消失）。回合顶部有一个开关“显示模型过程说明 · N”，打开后按原顺序看到全部旁白，行为等同第一轮的小字笔记。
- **阶段重点保留为正常消息。** 与 `update_plan` 在同一个模型步骤里发出的那句话，视为模型自己标出的阶段报告（`planUpdateNoteIds`，靠新增的工具条目 `stepId` 与助手条目的 `stepId` 相等判断，不看文字）。`update_plan` 在这类任务里调用很少（这次整个会话只有 2 次），所以这条只在模型自己用计划时才有内容，不假装有阶段摘要。
- **同类步骤折成一行。** 连续 3 步及以上同一类（命令、读取、搜索、浏览器操作、查找工具……）合成一行“查找工具 7 次 · 最近一条目标 ›”，点开才挂载各行；仍在执行的那一步始终露在收起的摘要下面。关着的工作记录不再把行渲染出来再用 CSS 藏起来。
- **对齐。** 实测发现普通工具行里图标中心比文字中心低 3.5px（行尾 22px 高的状态点把基线对齐的文字顶高了），改为垂直居中后偏差为 0；组内旁白文字原先比行标签靠左 9px，现在对齐；“阶段重点”消息对齐组标题；“执行中”那一行的缩进与展开后的子行一致。这些都做成了浏览器断言。

### 实测

同一份数据、150 步、无头 Chrome（只含脚本耗时，不含绘制）：

| 视图 | DOM 节点 | 挂载的行 | 追加一步的渲染中位数 |
| --- | ---: | ---: | ---: |
| 默认（旁白隐藏、同类折叠） | 502 | 0 | 14.6 ms |
| 显示旁白、每步一行 | 3376 | 121 | 35.8 ms |

旧布局的节点数约为默认视图的 6.7 倍。追加耗时仍随步数线性增长（每次更新都重算整个分组），这次没有处理。

### 没有做

- 没有让模型少调工具：MiniMax 一回复一个工具是它的习惯，依赖串行的浏览器操作本来也只能这样。减少的是无谓的搜索，不是有用的调用。
- 没有把旁白提升为“阶段摘要”：没有可靠的结构信号可用，不靠关键词或文字猜。

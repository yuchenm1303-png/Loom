# 运行时文字与组件的生成节奏：整体过一遍（2026-10-11）

起因：用户让我审视 Loom 运行时的文字生成与所有组件的生成节奏和逻辑——很多动画有卡顿或互相打架，消息流跟随最新位置时偶尔抖动——并且“每一处细节都要有精致的动画，可以加光效”。
这一轮没有凭感觉改：先做了一组测量工具（`desktop-react/scripts/motion-lab/`，下面的表），在**生产模式**的包上（开发模式的 `jsxDEV` 会把 React 的耗时放大几倍）逐帧、逐 DOM 变更地量，再改，再量，再用测试固定下来（每条新测试都做了变异检查：故意改坏代码，测试必须变红）。

## 量出来的问题和改法（提交按时间）

1. **常驻装饰是每帧都要交的样式重算税**（`ec043f6b`）。一次运行里每个还在跑的 CSS 动画都会让 Blink 在每个主线程帧重新解析它的元素，运行中又是每个 vsync 一帧（165 Hz 下 6 ms），所以侧栏的呼吸标记、环境光、运行点这类“永远在动”的装饰就是持续的开销。运行期间（`html[data-loom-live]`）把它们暂停，面板收起时也暂停。长回答场景：主线程忙 88% → 46%，样式重算 51% → 8%，帧 p95 17.6 → 7.8 ms，超过 33 ms 的帧 6 → 2。
2. **跟随最新位置用弹簧，并且在内容出现的同一帧响应**（`3085632e`、`45c29545`）。以前是 ResizeObserver 之后再等一帧去贴底，所以新内容先在视口外出现一帧、再整步跳上来，这就是“抖”。现在：临界阻尼弹簧（`followMotion.ts`，带速度、按缺口加刚度、闭式子步进，帧率无关），在 ResizeObserver 里（布局之后、绘制之前）就走第一步；页面逐帧增长时（动画在撑开内容）用更硬的弹簧贴住；写入对齐设备像素，跟随时关掉 `overflow-anchor`。运行中单帧 ≥12px 的滚动步 33 → 1，回头 3 → 1。
   还修了一个真 bug：React 提交到一半时（`removeChild` 在插入之前）强制布局会让页面短暂变矮，浏览器把 `scrollTop` 夹小，旧代码把它当成读者的滚动，结果完成时视图往错的方向走一步。现在这种夹小不当作读者的操作（夹小规则见 `TranscriptScrollController.followTick`）。
3. **流式文字的“半成品”不再露出来**（`02fd73f5`）：行尾的 `|`、`-`、`#` 这类标记、没写完的表格、被截在中间的英文单词，之前会闪一下再变成正确的样子。`streamingText.ts` 现在：表格要等分隔行写全才成表；孤零零的块标记（`-`、`#`、`1.`、`>`、`|`、`---`）等后面的内容再画；换行后的余数不算空行；英文单词不在绘制边缘被切断。
4. **每次更新的多余 CPU**（`6ec62839`）：Sidebar 记忆化、回收交接的视口刷新节流、滚动回声过滤、面板宽度、`MediaQueryList` 只建一个。13k 字回答忙 24% → 19%。
5. **打字边缘的光，和唯一的一条块出现规则**（`838fc8e3`）：最新几个字符发光，分三档先后熄灭，用 CSS Custom Highlight API（`::highlight()`），不往文字里插任何元素，所以消息在流式时和完成后是同一份 DOM。标题、引用、表格、代码块、公式、图片这些“成形的块”以前有两套互相打架的入场（还会留下恒等 transform 和 clip-path），现在只有 `loom-block-form` 一条（透明度加几像素位移，都在合成线程），代码块顶边多一道一次性的光线。
6. **决策卡原来是整张砸出来的**（`da98f28c`）：350px 高的卡片一帧出现，视图在三帧里跨过 337px。现在卡片属于完成后的回复（运行中的版面不画它，也等上面的文字画完），在完成的停顿里沿着“收起过程”同一条曲线、同样长度（380ms）展开：网格行从 0fr 到 1fr，用 clip 而不是 overflow（否则下面没出现的部分会算进可滚动高度，视图会冲到一张还没长出来的卡的底部），展开的前沿有一条细光线（深浅色各一套，代码块的光线也改用同一对变量）。历史、完成交接、减少动效下都不播放。页面逐帧增长时视图保持短弹簧（`TargetFlow` 只数增长，折叠不算），所以是跟着卡的下沿走（每帧 9–18px），不是追。
7. **完成时过程列表被无谓地建了两次**（`da98f28c`）：回合完成的那一次渲染还不是“停顿中”（停顿是 layout effect 里才设的），整段过程被当作历史画一遍（每一行重建），然后立刻按实时布局再画一遍；停顿和折叠结束后又被当作历史画一遍（隐藏的），380ms 后再丢掉。两处都去掉了：完成那一次渲染里直接就是停顿，折叠完的过程立刻释放。一次运行结束后创建/删除的 DOM 节点（code 场景）810/900 → 255/340，其中不再有步骤行。
8. **一个阶段结束时先变高再折叠**（`da98f28c`）：长的运行中阶段只显示最新 6 步和一行“更早的”；下一阶段开始时，正在收起的折叠被塞进了所有行，196px 一帧变成 336px，再折叠下去。折叠现在关闭时显示的是它打开时的内容。随机运行（fuzz）seed 40 里有一次 484px 的单帧步，就是它。
9. **结果标签的退出，和 Git 栏按钮**（`2d3c3d1e`）：“等待确认”标签在步骤继续时直接消失，旁边的时间被拽过去一个标签宽；现在标签带着原来的字和颜色收起 180ms（连同 flex 间距一起），时间被平滑带过去。项目、分支、变更、仓库/PR 这排按钮悬停时没有任何过渡，现在和邻居一样 150ms。
10. **字重实例的预热**（`c0a3d014`）：界面字体是可变字体，每个字重是首次排版时才创建的一个实例，约 7–10ms；样式里用了 32 个不同的字重（450、520、530……790），每个都落在第一次用到它的界面的第一帧上（设置页首次打开要建 6 个新的）。现在 App 空闲时每个空闲片段排版一个字重（`fontWarmup.ts`）。设置页首次打开（应用空闲 1.5 秒后）约 165ms → 120ms。

## 量的方法（`scripts/motion-lab/`）

| 脚本 | 回答什么 |
| --- | --- |
| `jitter.mjs` | 读者的眼睛看到的是否稳：每帧的滚动步、回头、地标位移、正在打的那一行的位移。 |
| `animations.mjs` / `style-cost.mjs` / `profile.mjs` | 运行中有哪些动画、各自动哪些属性（非合成属性每帧重算）；样式重算和布局的次数与原因（可 `--off` 关掉某组动画做对照）；主线程 JS 去了哪里。 |
| `screencast.mjs` / `contact.mjs` | 合成器真正产出的每一帧（带时间戳和最长间隔），和把它们排成一张联系表。 |
| `tour.mjs` | 整个界面一遍：侧栏、头部、检查器、设置各页、输入框各弹层、消息操作……每一步的最差帧、超 25ms 的帧数、意外位移；`--trace` 拆到脚本/样式/布局/绘制并指出谁强制了布局，`--popin` 列出没有任何动画就出现/消失的东西。 |
| `popin.mjs`（`popin-probe.mjs`） | 同上，用于运行中的场景。把“包一层”“换个父节点重新挂载”（原地替换）排除，只留真的无动画的出现和消失。 |
| `state-audit.mjs` | 悬停、聚焦、按下时样式变了却没有过渡的控件。（聚焦环瞬间出现是对的；`currentColor` 派生的边框色会误报。） |
| `fuzz.mjs` | 一个种子一次随机运行（多个阶段、批注、批准、并行调用、失败、结尾是回答/错误/停止/带决策卡），逐个检查：无页面错误、结束后什么都不再活着、过程已折叠、视图落在最新位置且跟随时只朝边缘移动、无无限动画残留、打字光已灭、DOM 不膨胀。失败的种子可单独重放。 |
| `conflicts.mjs` | 叠在一起的动效：嵌套元素同时淡入淡出（透明度相乘）、同一属性上有两个动画/过渡（现在会点名）。 |

全部干净：深色速度 4 的 48 个种子，浅色速度 2 的 24 个，英文速度 4 的 24 个，速度 10 的 24 个，成团的 provider 节奏（`?cadence=real`）的 12 个。

## 踩过的坑（下次量的时候）

- **性能剖面里“罪魁”常常只是替别人背锅**：完成时的卡顿在剖面上显示为 `followTick` 或 `removeChild`——因为布局是在它们读 `scrollHeight` / 删节点时被强制冲刷的，真正的原因是提交里建了两棵树。看 `LayoutInvalidationTracking` 的“Added to layout / Removed from layout”计数，和提交后创建/删除的 DOM 节点数，比毫秒数可靠得多。
- **单次测量被机器负载搅乱**（同一场景 57 / 164 / 213 ms）：比较要用“检出旧文件、跑 3 次以上、算工作量”的 A/B，不看单次毫秒。
- **开发模式不代表生产**：开发模式里完成时 200ms+ 的 rAF 间隙是 React 的开发期开销。
- **无头 Chrome 的合成是软件的**：弹层打开的最差帧里有 40–90ms 是 GPU 任务，不是主线程；要看主线程拆分，不是看最差帧。
- **冷启动成本是按（字重实例）和（字符 × 样式）收的**：新字重 7–10ms，新字号 0.3ms，同字重同字号下每个没见过的汉字 0.065ms，不同字体栈（雅黑放前面或放拉丁字体后面）没有区别。逐字预热测过，多省 15ms 要多花 250ms，不值得。

## 没有改、但量到的

- 设置页首次打开约 120ms（预热后）：是第一次排约 500 个对象加没见过的（字符 × 样式），主线程 JS 只有 ~20ms。
- 完成交接里最终回复仍是“从进程里的消息换成独立的最终回答条目”（重新挂载），这一帧约 25–55ms，主要是布局和样式，不是 JS；要消掉就要让这条消息始终在 React 树的同一个位置（portal/收养 DOM），没做。
- 代码块等块成形的那一帧，正在打的那一行会被推下去最多约 50px，随后视图滑回来（一次 2000 帧的运行里 4 次）；可以像决策卡那样做成高度展开，没做。
- 样式里 32 个不同的字重（650/660/640/620/610……）是设计层面的蔓延，收敛到几个会减少实例，但会改变字形的细微粗细，没做。
- 用户在回复中途点停止时，被压住的那段文字在停顿里一次出现约 108px（fuzz seed 6），很少见，没处理。
- 没有在真正的 Electron 里量：这台机器就是用户的机器（165 Hz），有头 Chrome 帧 p50 6.1ms，和 Electron 的渲染路径一致。

# 任务清单属于哪个请求（2026-11-08）

## 起因

`E:\ai run` 那个对话里，人问"总结一下我们现在的工作，接下来应该做什么，现在有哪些成果"。建造模式要求用工具前先列清单；
模型为了过这一关，把上一轮没做完的旧清单（修正 README、修正 §9、修正 plots.py、冒烟终检）原样交了一遍，然后按旧清单改起了文件。
手机上"对话任务"显示的也是这份旧清单。之前修的"删掉的未完成步骤保留为已放弃"管不到这里：它一步都没删。

根子在于：清单跨轮保留，上下文写着"跨轮继续未完成的工作"，闸门只看"这一轮有没有清单"，不看清单和这条消息有没有关系。

## 规则

每份清单记下它服务的请求：`request`（那条消息，前 200 字）和 `request_turn_id`（那条消息所在的轮）。
人发起的轮 = `turn_started.source` 是 `user` 或 `queue`，且不是"失败后原样重试"；长目标续跑、Host 替人重试都不算新请求。

| 情况 | 处理 |
|---|---|
| 没有清单 | 用工具前先为这次请求写清单（不变） |
| 旧清单已全部完成，人发了新消息 | 写的清单自动成为新清单（新 id、修订号 1、记 `previous_plan_id`），不要求说明，也不要版本号（`replace=true` 也一样） |
| 旧清单还有未完成步骤，人发了新消息，模型要继续它 | 必须带 explanation 说明这条消息是在继续；之后清单的 `request_turn_id` 记为这一轮 |
| 同上，但没有说明就原样交旧清单 | 拒绝，告诉它旧清单属于哪个请求、该怎么做（继续要说明，否则 `replace=true` 写新清单） |
| 同上，人问的是别的 | 不用工具就能答的问题不需要清单；其他工作用 `replace=true` 写新清单，旧的未完成步骤进 `dropped`，看得见 |
| 长目标续跑、重试 | 旧清单就是当前清单，照常继续 |
| 很早以前的旧清单（没有 `request_turn_id`） | 按最后写它的那一轮判断 |

模型每一步读到的清单上下文也分开写：属于之前请求的清单会标成"Task list from an earlier request: …，不是这一轮的清单，不要因为它在这里就去做它的活"；
闸门的拒绝提示同样点明。`update_plan` 的说明里写了这条规则。轻量事件视图里 `turn_started` 现在保留 `source` 和
`retrying_failed_input`，否则 Host 分不出谁发起了这一轮。

界面：清单属于之前的请求、而这一轮还没写自己的清单时，桌面任务面板顶部写"这份清单属于之前的请求「…」"，
建造页卡片标题变成"之前请求的任务清单"，手机面板标题变成"之前请求的任务"；工具栏的"进行中"标记不亮。

顺带：清单格式写错时，报错列出允许的值（如 outcome 的 passed/failed/…）或缺的字段；以前只说"违反 enum 规则"，
免费模型因此连错了五次。被拒的值本身仍不回显。

## 真实模型试跑（beam-free，免费；`C:\tmp\goal-live-tools\plan_trial.py`）

| 情形 | 第二条消息 | 结果 |
|---|---|---|
| A：第一轮只做一半就停 | "总结一下我们现在的工作……" | 没用任何工具，直接总结已完成和未完成的步骤；README 没被动 |
| B：同上 | "可以，继续把剩下的做完" | 继续旧清单，说明写"用户确认继续完成剩余步骤"，做完剩下两步 |
| C：第一轮做完 | "现在给 NOTES.md 写一段说明……" | 新清单（新 id，修订号 1，request 是新消息）；用 `replace=true` 时曾被要版本号，已改为不要 |

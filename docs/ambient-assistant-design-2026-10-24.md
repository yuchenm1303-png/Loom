# Ambient assistant implementation plan — 2026-10-24

Reuse Electron `entry.ts` single-instance bootstrap and `main.ts` Host transport. The Host owns the Python App Server; Desktop is an optional client. No second agent loop or OS service. Add an App Server owned scheduler with a SQLite ledger beside existing runtime settings, advisory single-owner lock, and a one-second code-only wake timer. Reuse `turn_start`, `_guard`, `_launch`, `turn_interrupt`, the runtime session lock, normal credential preparation and approval UI.

Separate responsibilities: `ambient.py` owns durable triggers/events/runs/notifications and admission budgets; `ambient_service.py` adapts existing service operations; production BrowserPolicy service owns start/close. Heavy project scheduling remains separate and must use the same service guard/admission and cancellation APIs, never infer project completion from a turn. No project continuation or interrupted-turn auto recovery.

Supported triggers: UTC epoch one-shot, fixed seconds interval (missed intervals coalesced to one), configured workspace-local file metadata changes, and explicitly delivered adapter event IDs. External platform adapters remain unconnected. No network sends. Results/notifications retained locally. A claimed run is never replayed after restart; unknown outcomes require human inspection. Cancellation disables its trigger and cancels its queue until explicitly enabled. Admission limits count automatic turns and measured token deltas; token caps are checked between turns, not hard in-flight provider limits.

UI: an Ambient assistant panel within Settings, with online/paused state, CRUD, cancellation, next due, runs/usage and local notices. Default monitoring costs no model calls. Tests cover restart, duplicate/coalesced events, busy sessions, approval, cancellation, budgets and live timer without a renderer.

## Research checked October 24–25

The official latest-release endpoints reported [OpenClaw v2026.10.7](https://github.com/openclaw/openclaw/releases/tag/v2026.10.7) and [Hermes v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5). These are observed versions, not an assumption that online documentation is frozen to those tags.

[OpenClaw Gateway](https://docs.openclaw.ai/gateway) documents a separately supervised gateway and lifecycle ownership. [Automations](https://docs.openclaw.ai/automation/cron-jobs) is its current scheduling surface; the [tagged CronService source](https://github.com/openclaw/openclaw/blob/v2026.10.7/src/cron/service.ts) delegates lifecycle, mutation and run operations instead of a perpetual model loop. Its evolving heartbeat configuration is deliberately not copied into Loom.

[Hermes cron documentation](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/website/docs/user-guide/features/cron.md) and [tagged scheduler source](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/cron/scheduler.py) separate gateway ticking from agent execution; the source explicitly describes a 60-second gateway ticker and cross-process tick lock. Loom's one-second timer, conservative restart review, workspace file source and between-turn budgets are our design choices, not claims of equivalent Hermes/OpenClaw behavior. No third-party service was installed or configured.

## Implemented interface and ownership

| Owner | Concrete interface / contract |
| --- | --- |
| Electron bootstrap | Existing `entry.ts` single-instance owner, `prepareDesktopHost`, `startHostTransport`, login-item and tray Quit Loom. Closing Desktop stops its renderer, not the Host. Existing updater `assertRestartSafe` remains authoritative. |
| Production BrowserPolicy App Server | Starts one `AmbientScheduler` after service construction; closes it before runtime shutdown and on `runtime.close`. The OS file lock prevents a second scheduler for the same Loom home. `ambient/list.online` means this scheduler thread is alive, not that every external capability is healthy. |
| Trigger storage | `<Loom home>/ambient.sqlite3` (WAL) stores tasks, event dedup receipts, logical runs, results, local notices and resource leases. `ambient.lock` is released on process exit. Indexed active-run queries avoid rescanning completed history on each tick. |
| RPC/UI | `ambient/list`, `ambient/history {before?,limit?}` (page through all runs), `ambient/put` (create or merge update by id), `ambient/pause {paused}`, `ambient/cancel {id}`, `ambient/delete {id}`, `ambient/event {id,key,source}`. The event endpoint requires an event task and uses the existing authenticated Host transport; it is not a public webhook. Initialize advertises `capabilities.ambient`. Settings → Ambient assistant offers the same controls. |
| Per-session admission | `AmbientServiceMixin.turn_start` serializes check/admit under the existing service `_guard`; `_launch` and runtime session locks remain the actual executors. `ServiceExecutor.ready/start/poll/cancel` provides a reusable internal adapter. A normal admission race raises `AdmissionBusy` and retains the queue. No new tool dispatcher or approval store. |
| Resources | `acquire_resources(operation_id, [names])` atomically reserves explicit exclusive names, e.g. `browser:profile`, `repo:integration`, or `port:3000`; `release_resources(operation_id)` releases after the caller verifies termination. Restart changes leases to `needs_review`, never expires them into duplicate operations. Leases are opt-in: existing tool-specific locks and provider behavior are unchanged. |
| Usage and notices | Run ids connect task/event/source, thread, turn, usage baseline and final delta. `maxRuns` and `maxTokens` are positive per-task admission limits; two automatic turns can be outstanding globally. Pending approvals also hold a slot. Notifications are local-only and suppress identical consecutive outcomes. Exact `AMBIENT_NO_CHANGE` results remain inspectable but create no notice. |

One-shot schedules preserve one pending wakeup if the Host was offline. Intervals coalesce missed periods into one wakeup and schedule the next interval from the current tick. File polling compares mtime/size/inode without reading contents; changes while busy merge into one pending wakeup. Fast changes that revert entirely between polls are not captured. Adapter message delivery must supply stable source event keys; payloads are not injected into the prompt. Task edits cannot reset measured counters or move outstanding runs to another thread.

Disable cancels queued wakeups; stop additionally interrupts active work and disables the task. Pause only prevents new scheduling/admission; admitted work and approvals remain visible and reconcile. Cancel is cooperative: completed external side effects cannot be rolled back. Deletion removes the task but preserves its run audit and notices. Re-enable is an explicit user operation. Changing task limits does not reset accumulated usage.

Before admission, `starting` is committed; after admission, the returned turn id is recorded. Restart never replays `starting`, `running`, `waiting_approval` or `cancelling` runs, disables those triggers and cancels their pending wakeups. Approval credentials are never stored in this ledger or automatically resumed. Normal known failures delay future triggered runs with exponential backoff capped at one hour; unknown outcomes require inspection rather than retry. A one-shot failure is retained, not silently replayed.

The heavy-project document's section 11 is a candidate broader API. This implementation supplies Host reuse, per-session admission/cancel, targeted durable event ingestion, explicit resource leases and local result notices. It does **not** implement a general cursor/ack event bus, a durable `operation_id → turn_id` idempotent gateway for project dispatch, provider budget reservations, fencing epochs or project ownership. Future Project Runner must add those contracts and use service admission, not submit a periodic ambient task to impersonate project recovery. A completed ambient turn makes no statement about a project's completion.

## Verification and operating limits

Validated in an isolated checkout with the bundled Python plus temporary test dependencies outside Git: `pytest tests/test_ambient.py tests/test_ambient_service.py tests/test_loom_host_background_runtime.py tests/test_event_index.py tests/test_app_server.py tests/test_app_server_local_ipc.py -ra`: **53 passed**. The live service timer test runs the real DurableAgentRuntime with a deterministic model fixture, without a renderer or connected RPC client, and waits for the actual timer to execute/reconcile a one-shot. No paid model call is needed. Other tests exercise real tool approval, preparation cancellation, busy queueing, restart receipts/review, file triggering, limits, backoff, resource locks, CRUD/history, cancellation failure persistence and notice suppression.

Renderer `tsc --noEmit` and full `vite build` passed in the isolated checkout with the exact staged settings integration. Vite reports the existing large-chunk advisory. The first full working-tree build was blocked by unrelated in-progress WebPortal imports (`portal-introduction.css` missing); no unrelated CSS was patched to make the task pass. A browser preview of the real AmbientSettingsPanel with test-only transport data verified Chinese rendering and save-to-edit behavior. Existing Host lifecycle tests establish the independent-window contract; this task does not claim a newly packaged installer or a physical sleep/logoff test.

On Windows, locking the screen leaves ordinary background code/network/file polling available while the session remains running; interactive desktop tools can fail or wait while locked. Sleep/hibernation stops this timer, network and model execution. Sign-out normally terminates the per-user Host; it is not a machine service. After reboot, existing configured login startup starts the Host when the user signs in. Missed triggers reconcile then, with the conservative policies above. No sleep execution or unattended interactive-desktop access is promised.

Budgets are measured between turns and may overshoot by one in-flight turn; they are not a provider billing cap. Crash-before-reconciliation usage may be incomplete and is labeled review-only. Local results and event receipts are retained indefinitely in v1; UI returns the newest 100 runs/notices, and archival/retention policies remain future work. External platforms, email/message delivery, calendar cron expressions and project recovery are not connected by this change.

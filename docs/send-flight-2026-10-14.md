# 发送：消息从输入框飞进对话，以及发送到开跑这一路（2026-10-14）

起因：用户说“检查一下消息发送过程到任务开始执行的整个链路是否流畅，另外给发送过程设计一个流畅灵动的动画，类似从输入框飞出到消息界面中，按你的审美随意设计”。
两件事：**量**这条链上哪里不顺（渲染、Host、Python 三段），修能修的；**设计**发送动画。动画的实现是 `src/sendFlight.ts` + `src/components/send-flight.css`，工具是 `scripts/motion-lab/flight-trace.mjs`、`flight-film.mjs`。

## 一、链路上量到的问题

### 渲染端（用 live-app 夹具加 `?latency=1200` 复现真实 Host 延迟）

| 现象 | 量到的 | 原因 / 处理 |
| --- | --- | --- |
| 发出后一秒多是一张静止画面 | 新一轮在 `turn-block is-complete`，没有过程区、没有“思考中”胶囊，胶囊在 1405 ms 才出现（= Host 的第一个事件到达） | `App.tsx` 的 `transcriptRunning` 自 2026-09-11（b3a738f5）起只信服务端状态。那次修复是对的（`currentTurnId` 在 `turn/started` 前还指着上一轮，把上一轮标成进行中会让它重排跳动），但连带让**刚发的这一轮**也被画成已完成。现在：服务端确认的一轮照旧；除此之外，带着一条 `status: "sending"` 的用户消息的那一轮从点击起就是进行中，且不报 `currentTurnId`，所以不会把上一轮误认。首页发第一条（要等 `thread/start`）同样适用 |
| 原来的发送进场动画从来没播过 | 探针里 `entry` 没有 `is-sending`，`getAnimations()` 为空 | 同上：挂载时 `active` 为假，`useState(active && !reduce)` 取了假。修好之后它会播，但已被下面的飞行取代（没有出发点时才用它） |
| 输入框的旧文字和新输入框叠在一起 | 约 140 ms（18–22 帧，旧文字不透明度峰值 .77–.81） | 交叉淡入的旧副本里还留着已发出的文字。发送时给 `.composer-mode-crossfade` 标 `data-sent`，副本里的文字透明，新输入框的占位符等文字飞走后再淡入 |
| 首页发第一条硬切 | 欢迎页、Token 卡、启动卡同一帧消失，气泡原地冒出 | 发送时把首页那一屏整个复制下来，在飞行层里 260 ms 淡出 |
| 多行消息发出时输入框一帧缩短 | 输入框区 289 → 192 px，旧副本被裁掉 | 旧副本保持自己的高度、贴底淡出（`send-flight.css`）。对话区本身仍是一帧变高（原有行为，没动） |

### Host（Electron 主进程）

- **每次发送前卡 1.2 s。** `turn/start` 先 `assertSignedInForModels()` → `verifyAuthenticatedSession()`：距上次校验超过 30 s 就请求 `/auth/me`，超时 1.2 s，超时按“服务不可达”放行。这台机器上 account.smirel.com 经代理，新建 HTTPS 连接的 TLS 握手就要 0.93–2.3 s（curl 总时间 1.3–2.7 s），用 Host 同样的 fetch 加 1.2 s 中止量了 11 次，**11 次全部超时**（不加限制的完整请求 0.9–4.9 s）。也就是每条隔了半分钟以上的消息，都白等 1.2 s 才转给 Python，而且这个校验在这条网络上从没真正完成过。
  现在（`accountClient.ts`）：校验在后台单飞地做，最长给 8 s；发送最多等 250 ms（`VERIFY_GRACE_MS`）。这段时间内答复了就和以前一样决定放不放行（拒绝就拦住），没答复就放行，后台答复回来后照常清会话（下一次发送被拦）、或记下已校验（30 s 内的下几条不再问）。以前超时放行本来就是“服务不可达也不拦本地使用”的既定行为，这里没有放宽，只是让快慢两种网络表现一致。
- **新对话的第一条还要再等一次模型权限检查。** `thread/start` 里 `assertModelSelectionAllowed` 会 `POST /policy/v1/check`（10 s 超时，这条网络上 1.5–5 s）。渲染端每 10 s 刷新一次模型列表（`MODEL_CATALOG_POLL_MS`），那一次已经取回了完整的权限快照。现在 20 s 内的快照里有这个模型的决定，就直接用它答复预检（同一个账号，登出/换号作废；快照里没有这个模型的决定仍然发 `/check`）。这只是预检，Python 端每个回合前仍然按租约 fail-closed 再查一次，所以最坏情况是多建了一个空对话，回合本身被拦。

### Python（app-server）

- **进程启动后的第一条消息多等 0.7–2.7 s。** 真实日志里自 10-09 起 13 次 `envelope_and_context` ≥ 700 ms（最长 2695 ms，包括只有 5 条消息的新会话），每次都是该 Host 进程的第一个请求，之后同类请求 40–130 ms。用真实 app-server 加一份真实 home 的副本（`scratch/send-chain/probe.py`，不调用模型）复现：第一个回合 `request_preparation_ms` 1742，其中 `capture_context` 984，里面 `_ensure_memory_backlog_scheduled` 745 ms（对每个会话 `last_event` ×146 = 242 ms，`memory_store.thread_state` ×103 = 334 ms，每次开一个新的 sqlite 连接）。这个扫描只是给上次没抽取的回合排队，当前请求用不到它。
  现在（`memory_runtime.py`）：扫描放到 `loom-memory-backlog` 守护线程，请求线程上只剩 0.5 ms；每个会话之间 `time.sleep(0)` 让出。同一探针：`capture_context` 984 → 82 ms，第一个回合 1742 → 769–993 ms，热回合 164–263 ms。
- 没动但值得知道：`connectors.py` 的 `build_step_context` 在连接器首次凭据检查（`gh` + api.github.com，经代理 1–5 s）没结束时最多等 3.0 s（`_INITIAL_REFRESH_STEP_WAIT_SECONDS`），这是故意的（别把 GitHub 工具绑成“未连接”），所以启动后几秒内发第一条仍可能多等；每一步的请求准备中位数约 0.45 s（`capture_context` 0.1 s + 其余 0.3 s）也没动。

## 二、发送动画

### 看到的

回车的瞬间，输入框里的字原地“离岸”，沿一条先升后滑的弧线飞向气泡的最终位置；气泡的底板（边框、底色、阴影）在飞行中从字的周围长出来，落地时带一点弹簧；落地后工具栏淡入，边缘亮一下，“思考中”紧接着出现。页面在底下同时给它让出位置，所以落点是它最终会在的地方。首页上，欢迎页在飞行底下淡出；补充要求（任务进行中再发）同样飞进正在运行的过程区；点首页的启动卡则从卡片出发，文字在途中淡入。

### 怎么做的（`sendFlight.ts`）

1. **出发点。** 回车时（清空输入框之前）`recordSendOrigin` 记下文字真实画在哪：第一行文字的左缘和行中心、字号、宽度（单行时）、以及输入框的外观。
2. **发起。** 对话区为这条消息挂出条目时，`UserEntry` 的 layout effect（绘制之前）调用 `launchSendFlight`。真实条目用 `data-flight="flying"` 压住（`visibility`，仍占着位置，所以页面已经是最终的高度），“思考中”的那一行也是一开始就预留（`grid-template-rows: 1fr; opacity: 0`），落地的页面不会再长高。
3. **两个副本。** 用 `cloneNode` 复制真实条目，放到 `.app-shell` 里的固定层：**文字**（无底板）和**底板**（内容隐藏）。克隆保证富文本、链接卡、附件、两种主题与落地后的真实气泡逐像素一致，不用另写一套渲染。
4. **只动合成器上的属性。** 文字平移（横向与纵向各用一条曲线，路径因此弯），起点缩放只用来把气泡字号对到输入框字号（单行按宽度对，这样一行的终点也对上，起飞第一帧与输入框的墨迹框完全重合）；底板淡入并带弹簧缩放（它没有字，所以可以缩放）。主线程忙（React 提交、会话列表刷新）时飞行不卡。
5. **落点预测。** 页面会让位：落点 = 条目现在的位置 − （页面最终滚动位置 − 现在位置），最终滚动位置是 `scrollHeight − clientHeight`（对话跟随到底）。飞行中每帧只改幽灵自己的 `left/top`，让落点跟着“页面此刻静止时条目会在的位置”走（流式输出把页面撑高、输入框换了高度都被吸收），低通滤波避免布局突变时跳。落地时再量一次真实条目，差 ≤ 1.5 px 直接交接，更大就用 110 ms 补一段。
6. **时间。** 时长 `330 + 0.18 × 距离` ms，限制在 380–540 ms；纵向 `cubic-bezier(.28,0,.2,1)`、横向 `cubic-bezier(.48,0,.25,1)`：出发很轻（起始速度是平均的 0.18 倍），约三分之一处最快（2.3 倍），75% 时走了 95%，路径偏离直线约 12%。“思考中”在 80% 时放行（缓动的长尾使消息此时已经基本到位），珠子的弹簧提前 70 ms 起。
7. **布局不同的消息。** 多行或在气泡里换行不同的消息，先把输入框里的文字按原样画一遍（`.send-flight-field`），起飞第一帧就是输入框的样子，前 22% 的时间里换成消息自己的排版。

### 没有飞行时

没有出发点（别处发的）、减少动态、窗口隐藏、消息高过窗口的 82%（或 520 px）、页面用 CSS zoom 缩放（Web 回退）、没有可对齐的文字（只有附件）：`launchSendFlight` 返回 false 并发出 `skip` 事件说明原因，条目走原来的进场（现在它真的会播）。飞行中条目被移除：幽灵随条目消失，不抛错。

### 量到的

- 起飞第一帧与输入框：墨迹框完全相同（`[9,20,746,42]` 设备像素），平均差 2.5/765（对宽度之前是 29）。
- 交接：幽灵最后一帧与真实气泡位置差 ≤ 0.12 px（对话、会滚动的页面、首页三种，生产构建）；像素差平均 0.65（浅色）–1.0（深色）/765，只有三个字母的边缘是亚像素差。
- 帧：生产构建、无头 Chrome 软件合成，整段超过 24 ms 的帧只有 1–3 个，都在回车后的 React 提交附近和落地附近（最长 35–61 ms，首页那次是首页换成对话的提交）。

## 四、没做、可以做

- **输入时预热。** 渲染端在第一次按键时让 Host/Python 预热（账号校验、权限检查、记忆扫描、第一次用到的导入），把网络等待藏在打字时间里。需要新的 IPC（preload、main、web 桥）和一个 `runtime/prewarm` RPC，改动面大，这次只做了不需要新接口的部分。
- 连接器首次检查最多等 3 s：可以在没有任何 GitHub 凭据（没有 `gh`、没有保存的连接、没有环境变量令牌）时不等。
- 每一步 0.45 s 的请求准备（长任务里每步一次）。
- 发送失败时气泡原样消失，可以让它飞回输入框。
- 对话区在多行消息发出时仍是一帧变高。

## 五、坑

- 在这个 shell 里用 heredoc 的 `node -` / `python` 写含 `\n`、反引号、正则的代码，反斜杠会被吃掉：这些内容一律用编辑工具写（这次踩了五回）。
- 暂停动画拍帧时，动画被 seek 到终点会触发 `finished`，飞行就落地了：停在终点前 2 ms；飞行的 `window.setTimeout` 保险丝（时长 + 260 ms）也要在拍摄期间拦住。
- 无头 Chrome 的屏幕截图帧不均匀（40–90 ms 一帧），看动作要用 `flight-film.mjs`（冻结+seek）或 `flight-trace.mjs`（每个 rAF 一行），不要用屏幕录像数帧。
- `StrictMode`（开发模式）会把 effect 跑两次：`launchSendFlight` 对同一个节点幂等，卸载检测推迟一个微任务（同一节点的重新挂载不算卸载）。
- Python 探针要复制一份真实 home 才能复现扫描开销（私有数据，放在被忽略的 `scratch/send-chain`，用完删除；不要复制 `control/app-server.lock`，那是用户正在运行的 Loom 的锁）。
